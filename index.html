FinanceGym

Point-in-time financial deep research benchmark

FinanceGym gives an agent a finance research question and a cutoff date. The agent may only retrieve documents published on or before that date, then writes a cited report. Reports are graded against expert rubrics that separate what was knowable at the cutoff from what actually happened afterwards. How the questions and rubrics are generated and validated is explained in the paper.

How the benchmark works

1. Retrieve, point-in-time

Every retrieval call is bounded by the task's cutoff date, so no document published after it can enter the evidence set. Enforcing that at the source is the benchmark's one hard rule.

2. Write a cited report

Any agent architecture is allowed — any loop, any planner, any backbone model. The single hard rule is point-in-time compliance on retrieval.

3. Graded on two axes

Pre-cutoff scores antecedent items against evidence available at the cutoff. Post-cutoff scores consequent items against what happened after. Rubrics stay withheld to prevent rubric hacking.

Leaderboard

Normalized rubric means (%) over the 400-question set. Pre-cutoff = grounding in evidence available at the cutoff, Post-cutoff = reasoning about what followed, ±SE = standard error of the Overall mean. System link points at the paper or repository for the agent framework the row runs on. Rank always reflects the overall standing, whatever column you sort by.

Run the benchmark, submit a report

Five steps: get the questions, set up cutoff-enforced retrieval, run your agent under the no-leakage rule, format an answers.jsonl, and send it to the maintainers. We run the judge and post your row on the leaderboard.

  1. Get the questions

    Take benchmark_400_public.jsonl from FinanceGym/data in the repository — see the data section above for the field reference.

    Download benchmark_400_public.jsonl ↗

  2. Bring a point-in-time retrieval setup

    The retrieval environment used for the published results is not distributed: the underlying documents are licensed CC BY-NC 4.0, which does not permit us to redistribute the corpus.

    Run your agent against whatever retrieval you like — your own index, a search API, an internal corpus — subject to one hard rule: it must return only documents published on or before the task's cutoff. How you enforce that is up to you; the self-check below is what we ask you to attest to.

    Scores from a different corpus are not directly comparable to the published rows, which all share one retriever. Submissions are listed with the retrieval setup they used.

  3. Run your agent — point-in-time, no leakage

    Any agent architecture is allowed: any loop, any planner, any backbone model. There is exactly one hard rule, and it is about retrieval.

    ● The hard rule: max_date is mandatory

    Every single /search call must carry max_date = that task's cutoff. The server then never returns a document published after the cutoff. Omitting it — even on one exploratory query — voids point-in-time compliance for the whole run.

    Whatever your retrieval is, the cutoff travels with every query:

    def search(query: str, k: int, cutoff: str) -> list[dict]:
    """Your retrieval, with the task cutoff applied at the source."""
    hits = my_retriever.search(query, k=k, max_date=cutoff)   # <- never omit
    for h in hits:                       # verify on the way back, too
        assert h["pub_date"][:10] <= cutoff, f"leak: {h['id']} @ {h['pub_date']}"
    return hits

    Post-cutoff self-check

    The server enforces the cutoff, but leakage can still enter through your own harness. Run these four checks before you submit — they are what we ask you to attest to on the submission form.

    CheckWhy it matters
    Every search carried max_date Log your search calls and assert the field is present on all of them. One unfiltered query is enough to leak.
    Assert pub_date <= cutoff client-side A cheap backstop against a misconfigured host or a stale cache. Treat any violation as a failed run, not a warning.
    Fetch only doc ids that search returned Fetching arbitrary ids — or falling back to the live web when a fetch fails — pulls in documents the point-in-time filter never saw.
    No live-web tool in the loop Disable any tool that can reach today's web during the run. Your cutoff-filtered retrieval must be the only evidence source.

    A minimal gate you can drop into your harness:

    def guarded_search(query: str, k: int, cutoff: str) -> list[dict]:
    """Search with the cutoff, then re-verify it on the way back."""
    hits = search(query, k, cutoff)
    for h in hits:
        pub = (h.get("pub_date") or "")[:10]
        if pub > cutoff:                       # ISO dates compare lexically
            raise RuntimeError(f"leak: {h['doc_id']} published {pub} > {cutoff}")
    seen_ids.update(h["doc_id"] for h in hits)
    return hits

def guarded_fetch(doc_id: str) -> str:
    if doc_id not in seen_ids:                 # never fetch what search didn't return
        raise RuntimeError(f"doc {doc_id} is outside the point-in-time evidence set")
    return fetch(doc_id)

    A note on the model's own memory

    A backbone model trained after the cutoff may simply know what happened next. We cannot audit that, and we do not ask you to unlearn it — but the report should stand on retrieved, cited evidence. Prompt your agent to assert only what its point-in-time sources support, and to cite each claim. Reports that recite post-cutoff outcomes without pre-cutoff grounding score poorly on the pre-cutoff axis anyway: the rubric rewards reasoning, not recall.

    One JSON object per line, one line per question — this is the exact shape our grader reads. See the full data format below.

  5. Send it to us

    See submission channels.

Data format for grading

A single JSONL file: one object per line, one line per benchmark question. 400 lines for a full run; partial runs are accepted but are marked as such on the leaderboard.

Fields our grader reads from each line of answers.jsonl.
FieldType RequiredDescription
questionstringrequired The benchmark question verbatim. This is the key that matches your answer to its withheld rubric — any edit, truncation, or added framing breaks the match and the line is dropped.
cutoffstring YYYY-MM-DDrequired The task's cutoff, copied from the question file.
reportstringrequired Your agent's full research report, with citations. Markdown is fine; it is graded as text. Do not wrap it in extra JSON.
searcheslist[string]optional The query strings your agent issued, in order. Used for retrieval-behaviour analysis, not scored.
docs_retrievedintoptional Number of documents your agent fetched.
stepsintoptional Number of search/reason iterations.
elapsed_sfloatoptional Wall-clock seconds for the task.

● Do not include the rubric

Submissions carrying a rubric field are rejected. The rubric is withheld by design, and a submitted one signals that the run was tuned against it.

Validate before sending

This checks the three required fields, rejects a stray rubric, and confirms every question matches the benchmark file exactly. 

import json

bench = {json.loads(l)["question"]: json.loads(l)["cutoff"]
         for l in open("benchmark_400_public.jsonl")}

seen, problems = set(), []
for i, line in enumerate(open("answers.jsonl"), 1):
    row = json.loads(line)
    for f in ("question", "cutoff", "report"):
        if not row.get(f):
            problems.append(f"line {i}: missing/empty {f}")
    if "rubric" in row:
        problems.append(f"line {i}: remove the rubric field")
    q = row.get("question", "")
    if q not in bench:
        problems.append(f"line {i}: question does not match any benchmark question verbatim")
    elif row.get("cutoff") != bench[q]:
        problems.append(f"line {i}: cutoff {row.get('cutoff')} != {bench[q]}")
    if q in seen:
        problems.append(f"line {i}: duplicate question")
    seen.add(q)

print(f"{len(seen)}/400 questions answered")
print("\n".join(problems) or "OK — ready to submit")

How grading works

Each question carries an expert-annotated rubric of 0–4 items, split into two categories. Antecedent items are verified against evidence available at or before the cutoff; consequent items are verified against what actually happened after it. Scores are normalized to a percentage and aggregated with bootstrap confidence intervals, which produces the three leaderboard columns:

  • Pre-cutoff — antecedent items: how well the report is grounded in what was knowable at the cutoff.
  • Post-cutoff — consequent items: how well it anticipated what followed.
  • Overall — the normalized mean across all rubric items, with its standard error.

Grading is single-blind and maintainer-run: the rubric is never shared, so no tuning to it is possible. The judge pipeline is reproducible and documented in docs/grading.md.

✓ What happens after you submit

We validate the file shape, run the judge over your reports, and add your row to the leaderboard, linked to your system's paper or repository. If anything about the submission is malformed or looks non-compliant, we come back to you before publishing a score.
